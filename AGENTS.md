# AGENTS.md — Политика репозитория agent-statusline

Единый репозиторий статус-лайнов для рабочих CLI-харнессов макбука. Источник правды — этот репозиторий (`~/dev/agent-statusline`); синхронизация рантайм-артефактов и привязок в конфигурационных файлах харнессов выполняется скриптом `sync.sh`:

- **Qoder CLI (`qoder`)**: скрипт `qoder/statusline-command.sh` → рантайм `~/.qoder-cn/statusline-command.sh` (доступен через симлинк `~/.qoder`) + секция `.statusLine` в `~/.qoder-cn/settings.json`.
- **Claude Code (`claude`)**: скрипт `claude/statusline.sh` (превью `docs/claude-example.svg`) → рантайм `~/.claude/statusline.sh` + секция `.statusLine` в `~/.claude/settings.json` (`STATUSLINE_SAFE_EFFORT="medium high xhigh" bash ~/.claude/statusline.sh`).
- **Codex CLI (`codex`)**: декларативный TOML-срез `codex/statusline.toml` → ключи `status_line` и `status_line_use_colors` в секции `[tui]` файла `~/.codex/config.toml` (без затрагивания секретов MCP-серверов и остальных таблиц `config.toml`).
- **Antigravity CLI (`agy`)**: скрипт `agy/statusline.sh` → рантайм `~/.gemini/antigravity-cli/statusline.sh` (файл `~/.gemini/antigravity-cli/settings.json` закрыт системной границей защиты Antigravity, поэтому `sync.sh` синхронизирует только скрипт; см. [analysis/2026-11-15-multi-harness-statusline-research.md](analysis/2026-11-15-multi-harness-statusline-research.md)).

Описание компонентов и публичный workflow — в `README.md` (публичный текст — английский); здесь — правила, которых README не покрывает.

## Связка с харнессом agent-skills

Этот харнесс — адаптация харнесса репо `~/dev/agent-skills` к проекту статус-лайнов CLI-харнессов (`qoder`, `claude`, `codex`, `agy`). Адаптация, а не редукция: переносится всё, что не противоречит природе проекта. Связка — **процедурная, а не ссылочная**: в политиках нет категории «принципы родителя», поэтому зависимость управляется механикой сверки, а не прямой отсылкой.

- **Пин.** `.harness-pin` хранит sha256 файлов харнесса родителя (`AGENTS.md`, `contracts/AGENTS.md`, `.hooks/pre-push`), дату последней адаптации этого репо и **базу каждого файла** — коммит родителя, из которого снят его хэш (`dirty(<HEAD>)`, если содержимое не совпадает ни с одним коммитом — снимок с рабочего дерева). Без базы чтение дельты сводится к перебору истории, а смешанность баз из пина не видна (случай пина 2026-08-17 — в research этой адаптации). Git-состояние родителя дальше не фиксируется: его коммиты — преимущественно доработка скиллов, к этому проекту отношения не имеют. `sync.sh` родителя не пинуется: это механика синхронизации каталогов скиллов, отличная от синхронизации статус-лайнов и срезов конфигов. Содержимое не копируется — зеркалирование запрещено.
- **Сверка.** `./harness-check.sh check` сравнивает текущее состояние родителя с пином. Расхождение (exit 1) запускает процедуру адаптации:
  1. Разобрать изменения родителя — от базы каждого файла, как её записал пин (`git -C ~/dev/agent-skills diff <база файла>..HEAD -- <файл>`); базу, помеченную `dirty` или отсутствующую, восстанавливать по дате и помечать в разборе как восстановленную.
  2. По каждому изменению решить, переносится ли оно в локальную адаптацию: изменение, конфликтующее с правилом этого репо, требует локальной правки; неприменимое к компонентам статус-лайна — отклоняется с записью в `analysis/`.
  3. Применить локальные изменения по правилам этого репо (contract-first там, где затронут компонент).
  4. `./harness-check.sh pin` — переписать пин по текущему состоянию родителя. Пин переписывается только после выполненной адаптации.
- **Периодичность.** Сверка выполняется перед релизом (пушем) и по запросу; при расхождении адаптация обязательна до пуша.
- **Локальность.** Правки решают задачи этого проекта подходящими средствами: объект контракта — компонент статус-лайна (`qoder`, `claude`, `codex`, `agy`), а не скилл; синхронизация — исполняемые скрипты и точечные срезы настроек (`.statusLine` в `settings.json` для `qoder`/`claude`, `[tui]` в `config.toml` для `codex`), а не каталоги скиллов; маппинг артефакт↔контракт объявлен в хуке (`OBJECTS`); BACKLOG отсутствует по построению. Репо родителя не синхронизирует, не зеркалирует и не гейтит этот репо.
- **Граница.** Правки харнесса родителя не вносятся из этого репо: изменения там идут в его собственном контрактном цикле (см. QA-1 в [`contracts/qoder.md`](contracts/qoder.md)).

## Жёсткие правила

- **Repo-first.** Правки компонентов вносятся в этот репозиторий, затем `./sync.sh push`. Правка прямо в рантайме допустима только как побочный продукт живой сессии — тогда `./sync.sh pull` (предупреждение и классификация дрифта) и только после явного подтверждения `./sync.sh pull --confirmed <component...>` (`qoder`, `claude`, `codex`, `agy`), до ближайшего коммита, не позже.
- **Не пушить при нарушениях.** После локальной активации (`git config core.hooksPath .hooks`) pre-push hook (`.hooks/`, скрытый — `sync.sh` его не трогает) блокирует `git push` при любом нарушении; перечень гейтов и их границы владеются шапкой `.hooks/pre-push`, здесь — только смысл. Код возврата чекера различает нарушение и отсутствие вердикта; непроверенное не считается проверенным и не пушится.
- **Сверка с родителем.** Перед пушем `./harness-check.sh check` чист (машинно — гейт сверки пина в перечне хука); при расхождении — процедура адаптации из секции «Связка с харнессом agent-skills».
- **Чужой дрифт — не свой коммит.** Если `sync.sh status` или `git status` показывают изменения, которые ты не делал, — не adopt и не коммитить молча: показать пользователю и решить.
- **Коммиты** — conventional (`feat:` / `fix:` / `docs:` / `chore:`), скоуп коммита = одно осмысленное изменение, без эмодзи. История до 2026-08-14 велась в императивном стиле и не переписывается.
- **Правка механики харнесса.** Изменения `sync.sh`, `.hooks/pre-push`, `.hooks/post-commit`, `harness-check.sh`, `AGENTS.md`, `contracts/AGENTS.md`, workflow в `README.md` — одним коммитом с независимым аудитом отдельным агентом: независимый аудит кода — для исполняемой механики (`sync.sh`, `.hooks/`, `harness-check.sh`), `audit-prompts` и `audit-causal-structure` — для нормативных текстов; объективные находки (в методологиях со шкалой — уровня Low+, без шкалы — каждый установленный дефект) устраняются тем же изменением или принимаются пользователем с записанным решением (сообщение коммита / `analysis/`). После правки хука или `harness-check.sh` прогонять их машинно: на чистом дереве (exit 0) и на подставном нарушении каждого гейта (exit 1).
- **Язык текстов.** Нормативные и служебные тексты репо — русский: корневые политики, контракты и журналы компонентов, комментарии механики харнесса; разметка (frontmatter, секции, ID) — английская. Исключение — `contracts/AGENTS.md`: он англоязычный, унаследован от родительской адаптации, и переписывается на русский только вместе со всей этой политикой. Английский обязателен для всего, что читает не этот репозиторий: `README.md`, комментарии и вывод артефактов статус-лайна, сообщения коммитов. Политика родителя (English-first и для нормативных текстов) не перенесена; основание и цена расхождения — в [analysis/2026-09-19-harness-adaptation-research.md](analysis/2026-09-19-harness-adaptation-research.md).

## Правка компонента

1. Эпизод `EP-N (status: pending)` в журнал `contracts/<component>-journal.md` — сначала: замысел дельты и список затронутых пунктов контракта; согласовать с пользователем. Компонент без пары контракт+журнал не редактируется: существующий без пары сначала получает backfill-контракт (снимок текущего состояния) + журнал, новый — проектируемую спецификацию + журнал с `EP-1 (status: pending)`.
2. Гомогенизация контракта по RULE-homogenization (двунаправленная сверка), затем аудит черновика контракта по RULE-audit-pass (независимый проход отдельным агентом; находки и disposition — в журнал).
3. Правка артефакта компонента (`qoder/statusline-command.sh`, `claude/statusline.sh`, `codex/statusline.toml` или `agy/statusline.sh`) по контракту.
4. Доработка контракта, если реализация разошлась с замыслом эпизода (коррекция — в журнал); аудит рендера по RULE-audit-pass.
5. `./sync.sh push` → `./sync.sh status` чист → статус эпизода implemented → коммит → пуш (pre-push гейты). Один эпизод = один коммит; пуш посреди эпизода запрещён.
6. Если изменилось видимое пользователю поведение — обновить соответствующую секцию в `README.md` (и при необходимости `docs/claude-example.svg`) тем же или отдельным `docs:`-коммитом.

## Контракты и исследования

Контракты — постоянные, объектно-центричные: один контракт на компонент в паре с журналом `<component>-journal.md` (модель snapshot + ledger: `tgwizard` → `~/dev/agent-skills` → этот репо). Контракт — гомогенизированная текущая спецификация, единственный нормативный источник, без маркеров версий; журнал — provenance (эпизоды, коррекции, хроника), нормативной силы не имеет. Директории `contracts/`, `analysis/` и `docs/` — не синхронизируемые рантайм-компоненты: `sync.sh` синхронизирует только артефакты статус-лайнов и их срезы настроек.

- **MUST** — у каждого компонента из `OBJECTS` есть постоянный контракт `contracts/<component>.md` и журнал `contracts/<component>-journal.md` (появляются не позже первой правки компонента): контракт — исчерпывающая спецификация, из которой артефакт компонента восстановим практически как он есть. Контракт стоит впереди компонента: артефакт — рендер контракта для рантайма.
- **MUST** — правка компонента без пары контракт+журнал не допускается; компонент без пары сначала получает backfill-контракт (фиксирует текущее состояние) и журнал, согласованные с пользователем, — и только затем редактируется.
- **MUST** — цикл правки: эпизод в журнал (pending) → гомогенизация контракта со сверкой (RULE-homogenization) → аудит черновика по RULE-audit-pass → правка артефакта по контракту → аудит рендера по RULE-audit-pass → при расхождениях уточнение контракта и коррекция в журнале → статус эпизода implemented.
- **MUST** — контракт никогда не позади кода: он равен ему или опережает его.
- **MUST** — нормативная сила только у контракта: артефакт правится по контракту, запись журнала источником правки не является.
- **MUST** — удаление компонента тем же изменением удаляет его контракт, журнал, строку IDX и секцию в README; архив — git-история.
- **MUST** — правила авторства, нумерации и индекс контрактов — в [`contracts/AGENTS.md`](contracts/AGENTS.md).
- **MUST** — исследование, на которое опирается контракт, лежит в `analysis/YYYY-MM-DD-<тема>-research.md` и явно указано в `refs` контракта.
