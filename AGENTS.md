# AGENTS.md — Политика репозитория qoder-cli-statusline

Статус-лайн Qoder CLI: единственный компонент `statusline-command.sh`. Источник правды — этот репозиторий; рантайм — `~/.qoder-cn/statusline-command.sh` (доступен через симлинк `~/.qoder`), синхронизируется `sync.sh`. Описание компонента и публичный workflow — в `README.md` (публичный текст — английский); здесь — правила, которых README не покрывает.

## Связка с харнессом qoder-skills

Этот харнесс — адаптация харнесса репо `~/dev/qoder-skills` к проекту с одним компонентом (там — множество скиллов; здесь — только статус-лайн). Адаптация, а не редукция: переносится всё, что не противоречит природе проекта. Связка — **процедурная, а не ссылочная**: в политиках нет категории «принципы родителя», поэтому зависимость управляется механикой сверки, а не прямой отсылкой.

- **Пин.** `.harness-pin` хранит sha256 файлов харнесса родителя (`AGENTS.md`, `contracts/AGENTS.md`, `.hooks/pre-push`) и дату последней адаптации этого репо. Git-состояние родителя не фиксируется: его коммиты — преимущественно доработка скиллов, к этому проекту отношения не имеют. `sync.sh` родителя не пинуется: это механика синхронизации скиллов, для одного компонента нерелевантная. Содержимое не копируется — зеркалирование запрещено.
- **Сверка.** `./harness-check.sh check` сравнивает текущее состояние родителя с пином. Расхождение (exit 1) запускает процедуру адаптации:
  1. Разобрать изменения родителя (`git -C ~/dev/qoder-skills log --since=<дата пина> -p` по файлам пина).
  2. По каждому изменению решить, переносится ли оно в локальную адаптацию: изменение, конфликтующее с правилом этого репо, требует локальной правки; неприменимое к одному компоненту — отклоняется с записью в `analysis/`.
  3. Применить локальные изменения по правилам этого репо (contract-first там, где затронут компонент).
  4. `./harness-check.sh pin` — переписать пин по текущему состоянию родителя. Пин переписывается только после выполненной адаптации.
- **Периодичность.** Сверка выполняется перед релизом (пушем) и по запросу; при расхождении адаптация обязательна до пуша.
- **Локальность.** Правки решают задачи этого проекта подходящими средствами: объект контракта — компонент, а не скилл; синхронизация — один файл, а не каталоги; маппинг артефакт↔контракт объявлен в хуке; BACKLOG отсутствует по построению. Репо родителя не синхронизирует, не зеркалирует и не гейтит этот репо.
- **Граница.** Правки харнесса родителя не вносятся из этого репо: изменения там идут в его собственном контрактном цикле (см. QA-1 в `contracts/statusline.md`).

## Жёсткие правила

- **Repo-first.** Правки скрипта вносятся в этот репозиторий, затем `./sync.sh push`. Правка прямо в рантайме допустима только как побочный продукт живой сессии — тогда `./sync.sh pull` (предупреждение и разбор дрифта) и только после явного подтверждения `./sync.sh pull --confirmed statusline` (дрифт разобран), до ближайшего коммита, не позже.
- **Не пушить при нарушениях.** После локальной активации (`git config core.hooksPath .hooks`) pre-push hook (`.hooks/`, скрытый — `sync.sh` его не трогает) блокирует `git push` при любом из нарушений: (1) `./sync.sh status` не чист; (2) у компонента нет контракта `contracts/statusline.md`, журнала `contracts/statusline-journal.md` или строки IDX (backlog пре-контрактных компонентов отсутствует по построению).
- **Сверка с родителем.** Перед пушем `./harness-check.sh check` должен быть чист; при расхождении — процедура адаптации из секции «Связка с харнессом qoder-skills».
- **Чужой дрифт — не свой коммит.** Если `sync.sh status` или `git status` показывают изменения, которые ты не делал, — не adopt и не коммитить молча: показать пользователю и решить.
- **Коммиты** — conventional (`feat:` / `fix:` / `docs:` / `chore:`), скоуп коммита = одно осмысленное изменение; публичный текст репо — английский, без эмодзи. История до 2026-08-14 велась в императивном стиле и не переписывается.
- **Правка механики харнесса.** Изменения `sync.sh`, `.hooks/pre-push`, `harness-check.sh`, `AGENTS.md`, `contracts/AGENTS.md`, workflow в `README.md` — одним коммитом с независимым аудитом отдельным агентом: audit-code — для исполняемой механики (`sync.sh`, `.hooks/`, `harness-check.sh`), audit-prompts — для нормативных текстов; объективные находки (у audit-code — уровня Low+) устраняются тем же изменением или принимаются пользователем с записанным решением (сообщение коммита / `analysis/`).

## Правка компонента

1. Эпизод `EP-N (status: pending)` в журнал `contracts/statusline-journal.md` — сначала: замысел дельты и список затронутых пунктов контракта; согласовать с пользователем. Компонент без пары контракт+журнал не редактируется: существующий без пары сначала получает backfill-контракт (снимок текущего состояния) + журнал, новый — проектируемую спецификацию + журнал с `EP-1 (status: pending)` (здесь пара установлена вместе с харнессом — backfill).
2. Гомогенизация контракта по RULE-homogenization (двунаправленная сверка), затем аудит черновика контракта по RULE-audit-pass (независимый проход отдельным агентом; находки и disposition — в журнал).
3. Правка `statusline-command.sh` по контракту.
4. Доработка контракта, если реализация разошлась с замыслом эпизода (коррекция — в журнал); аудит рендера по RULE-audit-pass.
5. `./sync.sh push` → `./sync.sh status` чист → статус эпизода implemented → коммит → пуш (pre-push гейты). Один эпизод = один коммит; пуш посреди эпизода запрещён.
6. Если изменилось видимое пользователю поведение — обновить таблицу сегментов в `README.md` тем же или отдельным `docs:`-коммитом.

## Контракты и исследования

Контракты — постоянные, объектно-центричные: один контракт на компонент в паре с журналом `<component>-journal.md` (модель snapshot + ledger: `tgwizard` → `~/dev/qoder-skills` → этот репо). Контракт — гомогенизированная текущая спецификация, единственный нормативный источник, без маркеров версий; журнал — provenance (эпизоды, коррекции, хроника), нормативной силы не имеет. Директории `contracts/` и `analysis/` — не компоненты: `sync.sh` синхронизирует только файл статус-лайна.

- **MUST** — у компонента есть постоянный контракт `contracts/statusline.md` и журнал `contracts/statusline-journal.md` (появляются не позже первой правки компонента): контракт — исчерпывающая спецификация, из которой `statusline-command.sh` восстановим практически как он есть. Контракт стоит впереди компонента: скрипт — рендер контракта для рантайма.
- **MUST** — правка компонента без пары контракт+журнал не допускается; компонент без пары сначала получает backfill-контракт (фиксирует текущее состояние) и журнал, согласованные с пользователем, — и только затем редактируется.
- **MUST** — цикл правки: эпизод в журнал (pending) → гомогенизация контракта со сверкой (RULE-homogenization) → аудит черновика по RULE-audit-pass → правка `statusline-command.sh` по контракту → аудит рендера по RULE-audit-pass → при расхождениях уточнение контракта и коррекция в журнале → статус эпизода implemented.
- **MUST** — контракт никогда не позади кода: он равен ему или опережает его.
- **MUST** — нормативная сила только у контракта: скрипт правится по контракту, запись журнала источником правки не является.
- **MUST** — удаление компонента тем же изменением удаляет его контракт, журнал, строку IDX и строку в README; архив — git-история.
- **MUST** — правила авторства, нумерации и индекс контрактов — в [`contracts/AGENTS.md`](contracts/AGENTS.md).
- **MUST** — исследование, на которое опирается контракт, лежит в `analysis/YYYY-MM-DD-<тема>-research.md` и явно указано в `refs` контракта.

## Соседние репозитории и скиллы

`~/dev/qoder-skills` — источник адаптации харнесса; связка — пин-процедура (`harness-check.sh`); репо не синхронизируется и не зеркалируется. Скилл `publish-statusline` (там) исторически публиковал этот репо из рантайма; с введением repo-first он трактуется как legacy-транспорт до правки в цикле родителя (QA-1 в `contracts/statusline.md`). Не создавать механических копий артефактов этого репо куда-либо ещё.
