## Purpose {#purpose}

This directory contains permanent, component-centric Design Contracts. Each component in this repository (`qoder`, `claude`, `codex`) is described by a pair of files: a contract and its journal.

- The **contract** is the homogenized present-tense specification of the component: the single normative source, carrying no version markers. **MUST** — the contract is exhaustive enough that the component artifact (`qoder/statusline-command.sh`, `claude/statusline.sh`, or `codex/statusline.toml`) can be recreated from it practically as-is. The artifact is the runtime render of the contract; the contract leads.
- The **journal** is the provenance ledger: change episodes with their intent, corrections, and the technical chronicle. The journal has no normative force.

Model inherited from the parent harness `~/dev/agent-skills` (`contracts/AGENTS.md` there), which itself adapts the flagship repo `tgwizard`; this repo adapts it to a multi-harness status-line project. The link to the parent harness is procedural, not referential: a hash pin plus a periodic adaptation check (`harness-check.sh`), declared in the root `AGENTS.md`.

- **MAY** — prose content may be written in Russian; the language boundary belongs to the root `AGENTS.md` («Язык текстов»), and markup keys stay English.
- **MUST** — LLM markup structure (frontmatter fields, anchors, item IDs, section names) remains in English.

## Structure {#structure}

Every file in this directory is one of: (a) this AGENTS.md index, (b) a component contract (`<component>.md`), or (c) a component journal (`<component>-journal.md`). No BACKLOG file exists by construction: the contract system was installed together with each component, and a new component may not exist without a contract; agreed refactor proposals live as Risks/Q&A entries in the component contract (precedent: QA-1) or as `analysis/` research, not in a separate store.

- **AGENTS.md role** — single entry point: contract index, status, and operational rules.
- **Contract role** — homogenized current specification. Required body sections: Map, Purpose, Invariants, Specification, Acceptance gates, Risks, Q&A. The contract carries a pointer to its journal (Map and frontmatter `refs`). No Scope sections, no History, no Implementation status, no version markers: normative deltas are folded into the body at change time (see the change cycle), and their record lives in the journal.
- **Journal role** — provenance ledger, strictly non-normative: the artifact is never edited from a journal entry. Content: episodes (`EP-N`) carrying delta intent and the list of touched clauses, correction entries, audit-pass records (findings and their disposition), and the chronicle (`CHANGE-*`). Episode status: `pending → implemented | cancelled`; only the status field mutates, the intent text never does (inline supersession pointers inside migrated intent text, e.g. `*(Superseded: EP-N…)*`, are read-only annotations, not mutations). The journal is created together with the contract: for a new component it starts with `EP-1 (status: pending)` carrying the designed specification, rendered into the artifact and marked `implemented` in the same creation commit; for a backfilled component `EP-1` carries the snapshot of the current state.
- **Reconstruction** — the contract alone is the current truth; no derivation from deltas is ever required to read or edit a component.
- `analysis/*.md` holds research artifacts; contracts reference them via `refs` frontmatter and inline links. Research is not normative; a contract clause is.
- **Boundary** — repo-level mechanics (sync, runtime deploy, settings/config slice injection, hooks, release flow, parent-harness pin) never belong in a component's Specification: the component is harness-deployment-neutral, and repo-level mechanics live in the root `AGENTS.md` and `README.md`. Acceptance gates MAY carry repo mechanics of the change procedure (sync/push/status checks). The parent's boundary exception for `release-skills` (repo mechanics as its user-visible capability, user-confirmed in the parent repo) does not apply here: no component of this repo has repo mechanics as its capability (see the adaptation research).

## Change cycle {#change-cycle}

One change episode:

1. Design the delta against the agreed requirements; identify the intended improvement and evidence that can support its acceptance.
2. Record it as journal episode `EP-N (status: pending)` — intent text plus the list of touched clauses.
3. Homogenize: fold the delta into the contract per RULE-homogenization (draft → independent bidirectional reconciliation → classify residuals → iterate until zero unclassified residuals).
4. Audit the contract draft per RULE-audit-pass: an independent pass by a separate agent over both text methodologies the rule names; objective defects are fixed or accepted with a recorded decision; outcome and dispositions go to the journal.
5. Optional: journal corrections discovered while folding or auditing.
6. Edit the component artifact (`qoder/statusline-command.sh`, `claude/statusline.sh`, or `codex/statusline.toml`) per the contract only, then `./sync.sh push` so that `./sync.sh status` is clean.
7. Audit the rendered artifact per RULE-audit-pass (the render is a new artifact and may carry defects the contract lacks); optionally refine the contract if implementation diverged — any deviation from the episode intent is recorded as a correction entry in the journal.
8. Episode status → `implemented`.

- Creation of a new component follows the same episode shape, in one commit: contract (designed specification) + journal starting with `EP-1 (pending)` + IDX line here + the artifact per the contract + sync + the RULE-audit-pass audits; `EP-1` is marked `implemented` in that commit. For a backfill, the audit runs on the snapshot and never silently edits it: findings are accepted (recorded) or open the next episode once EP-1 is closed.
- One episode = one commit (journal + contract + artifact + sync), made after the episode status is `implemented` — the render audit of step 7 runs before the commit. No push mid-episode.
- Invariant: the contract is never behind the code — it equals it or leads it.

## Operational rules {#rules}

- **RULE-contract-monopoly** — normative force belongs to the contract alone. The component artifact is edited per the contract only; a journal entry is never the source for a code edit.
- **RULE-one-contract-per-component** — one contract + one journal per component: `contracts/<component>.md` and `contracts/<component>-journal.md`. A change episode never gets its own contract file; it is recorded as an episode in the component's journal and folded into the contract.
- **RULE-contract-first** — a component is never edited without its contract + journal pair: the episode cycle above is the only way a component change happens, and a component without a pair first receives a backfill contract (snapshot of the current state) + journal approved by the user. There is no trivial-wording bypass.
- **RULE-reconstructability** — the contract carries the component's full normative content as the homogenized present. If the artifact and the contract disagree, classify the discrepancy against the agreed intent: correct an erroneous artifact to the contract; amend the contract first only for a justified, intended semantic change or a genuine contract gap resolved under RULE-homogenization. Record that decision or correction and update all affected clauses and the artifact in the same episode. Preserve the user's intended outcome and the strength of acceptance criteria: a criterion the implementation fails stays unmet until it is fulfilled or the user explicitly changes it; silent drift and amendments that merely ratify an implementation defect are defects.
- **RULE-homogenization** — folding a delta into the contract is iterative: draft from (contract + delta); independent bidirectional reconciliation by a separate pass/agent (every clause of the source has an image in the draft; every clause of the draft has a source); each residual classified as (a) folding error → fix, (b) editorial integration → journal note, (c) contract gap or contradiction → resolve from established intent and applicable requirements, recording the grounds; seek a user decision only where materially different outcomes remain unresolved or the root authority rules require one. Stop when zero unclassified residuals remain. Minimal executable form: a fresh re-read of the contract and the delta without relying on the draft; a separate subagent when available. A residual requiring a user decision keeps the episode `pending` with that decision explicit; continue independent work while it is pending. Migration of a legacy delta chain is one fold of the full chain; residuals in class (c) are questions about the current state only.
- **RULE-audit-pass** — a contract draft and the artifact rendered from it pass an independent audit by a separate agent. Normative text carries two methodologies: `audit-prompts` (does the text produce the intended behavior) and `audit-causal-structure` (are its claims and the dependencies between them supported); where a skill is unavailable, an equivalent pass applies its methodology. The contract pass examines the agreed specification; the render pass examines what the runtime executes or consumes, including transfer fidelity, dependencies and execution context. Scope each pass to the consequential questions it can settle. For executable mechanics (commands, paths, sync/hook behavior — as this repo's components have), the render pass additionally includes an independent code audit for mechanical fidelity. Research under `analysis/` owes no audit.
  - For an initial independent judgment, provide a self-contained task with the target's purpose, governing requirements, actual artifacts and relevant dependencies. Include the context needed to judge the target; isolation does not justify withholding a requirement or a source that can settle a finding. Keep the author's diagnosis, preferred verdict, prior audit conclusions and expected execution answers outside that initial context. Do not consult those conclusions through memory, journals or research summaries before forming the initial judgment. A new agent with inherited conclusions is not an independent initial reviewer. If higher-priority or automatically supplied context makes prior exposure unavoidable, disclose what was exposed and treat the result as supplemental; the required independent judgment remains outstanding. After recording the initial judgment, reconcile previous findings and disagreements explicitly. Targeted verification of an identified fix may use the earlier finding; it is not a new independent discovery claim.
  - Where a mechanical check exists for the claim, run it and report what it covered instead of re-deriving the same verdict by reading. The checks this repo guarantees are the pre-push gates (inventory: `.hooks/pre-push`); ad-hoc tooling (a shell linter, a payload battery) is run where available and named as such in the report. A check that cannot reach a verdict is reported as unchecked, never as a pass.
  - Findings are objective defects only (evidence, consequence, proposed change, disposition; severity when the invoked methodology requires it); the epistemic channel is falsifiability — a proven finding with evidence versus an open question with missing evidence — not a graded confidence; stylistic preferences are not findings. Findings at Low and above, and every established defect of a methodology that does not grade, are fixed in the same change or accepted by the user with a recorded decision.
  - Iteration: fix → re-audit; if that re-audit changes the artifact, use at most one further full discovery pass, then focus on verifying the remaining fixes and the requirements they affect. Every final fix receives this targeted verification against the resulting artifact, including applicable machine checks; do not restart a full discovery audit without a concrete new concern. A newly exposed objective defect still needs resolution or recorded user acceptance. Reaching an iteration limit never establishes completion. The pass closes when zero objective defects remain or the remaining ones are accepted by the user with a recorded decision; an unresolved defect without user access leaves the episode `pending` with the defect enumerated. Outcomes and residual dispositions are recorded in the journal (episode body and/or chronicle).
  - Minimal form for a wording-only single-clause delta: a fresh independent re-read of the changed sections with their immediate context instead of a full pass; a separate subagent when available. For a backfill episode the audit runs on the snapshot and never silently edits it: findings are accepted with a recorded decision or, unresolved without user access, leave the episode `pending`; agreed fixes open the next episode.
- **RULE-render-parses** — each component artifact is verified mechanically according to its format, not only as prose: shell scripts parse under their declared shebang dialect (`dash -n` / `sh -n` for `#!/bin/sh`, `bash -n` for `#!/usr/bin/env bash`) and degrade rather than fail on empty/minimal input; declarative TOML slices (`*.toml`) parse cleanly with only the allowed `[tui]` table and typed keys (`status_line`, `status_line_use_colors`). The check lives in the pre-push gate inventory (Gate 4); a run that could not reach a verdict is reported unchecked, never passed.
- **RULE-journal-additive** — journal entries are added; of an existing entry only the status field mutates; deviations, cancellations, and late corrections are new entries referencing the original.
- **RULE-pending-single** — a journal holds at most one pending episode. A session that finds a pending episode first completes or cancels it (cancellation is a correction entry referencing the episode); no new episode is opened until the pending one is closed.
- **RULE-episode-numbering** — `EP-1`, `EP-2`, ... strict sequential integers per journal. Never reuse, never delete.
- **RULE-gate** — acceptance criteria are contract clauses (`GATE-N`). Outcomes available before the implementation commit are recorded in the journal — in the episode body (`GATE-N: pass|fail — <grounds>`) and/or the chronicle. For a gate with requirements that can only be checked after that commit or its publication (or only against the live CLI session), record the already verifiable component results at their applicable stages; only the later components are deferred. A failed required component makes the gate fail unless that residual is explicitly accepted under the applicable rules; without such failures, unchecked required components keep the gate unverified. Never record the whole gate as passed before every required component is verified or its residual accepted where permitted. The journal records the remaining components as unverified and names the intended report location (the release response in the task conversation, a later chronicle entry, or a separately retained release artifact). After the authorized operation, that report records the exact commit ID (where applicable), each deferred gate and its actual verdict and evidence, including any failure or missing check; a release-response report does not require another episode commit. Never pre-record a pass. A release is complete only when all its required gates are verified or their residuals explicitly accepted under the applicable rules; `implemented` alone does not establish release completion. Gate numbering is sequential, never reused, never deleted. Gates for future episodes are worded generically (what is checked on any change of the kind), so the acceptance section does not accumulate vacuous criteria.
- **RULE-invariant-supersession** — an `INV-N` may be revised when it no longer describes the active component. Keep its identifier stable; the prior wording and the rationale live in the journal episode or correction.
- **RULE-provenance** — the contract carries no inline lineage: no episode or correction id, no narrative of how a clause came to stand (the journal pointer as pair-member is not provenance). Each episode lists the contract clauses it touches (INV, GATE, RISK, QA, Specification sections); a clause's lineage is reconstructed by searching its ID in the journal. Risks and Q&A keep the digest of the positions that stand now — a decision with its reason, a rejected alternative with why — as the contract's own present, never as a record of the change that produced it.
- **RULE-contract-gate** — the pre-push hook fails a push when any component artifact lacks `contracts/<component>.md`, `contracts/<component>-journal.md`, or an IDX line here. There is no backlog mechanism: the system started with every component covered, and a new component may not be added to any backlog list (see RULE-contract-first).
- **RULE-references-resolve** — a reference must reach its target. Every markdown file in `contracts/` is this `AGENTS.md` index, `<component>.md`, or `<component>-journal.md` for a component listed in the pre-push hook's `OBJECTS`. For a relative markdown link in a tracked `.md` file, the target resolved from the containing file's directory must exist and its normalized path must remain inside the repository; an escaping target is a defect even when it exists on disk. Scheme-ful (`http(s):`, `ftp:`, `mailto:`, `data:`) targets and pure anchors (`#section`) are not repo paths; the anchor half of a link (`file.md#section`) is checked in review. Verify: `.hooks/pre-push` gates 2 and 3.
- **RULE-obsolescence** — when a component is removed, its contract, journal, IDX line, and README line are removed in the same change; git history carries the archive. No tombstones.
- **RULE-cross-refs** — a change touching several contracts updates all of them; link contracts and `analysis/` files with Markdown links.

## Naming conventions {#naming}

- **File naming** — contract: `contracts/<component>.md`; journal: `contracts/<component>-journal.md` (kebab-case). The component name identifies the target CLI harness (`qoder`, `claude`, `codex`), while the artifact lives under its subdirectory (`qoder/statusline-command.sh`, `claude/statusline.sh`, `codex/statusline.toml`); the artifact ↔ contract mapping is listed in the pre-push hook's `OBJECTS`.
- **Section anchors** — contract: `#map`, `#purpose`, `#invariants`, `#specification`, `#gates`, `#risks`, `#qa`; journal: `#episodes`, `#chronicle`.
- **Item IDs** — line-start IDs: `INV-N`, `GATE-N`, `RISK-N`, `QA-N` (contract); `EP-N` (journal episodes); `CHANGE-YYYY-MM-DD-<tag>` (chronicle).
- **Contract frontmatter** — `id`, `title`, `kind: contract`, `status`, `created`, `updated`, `owners`, `refs` (journal link included). No content-version field.
- **Journal frontmatter** — `id`, `title`, `kind: journal`, `contract` (pointer to the contract), `created`, `updated`.
- **Q&A entries** — carry either `Decision:` (accepted or rejected, with date and confirmation) or `Status: open|resolved|rejected`; one scheme per entry, consistent within the contract.

## Adaptation notes {#adaptation}

Differences from the parent harness `~/dev/agent-skills`, deliberate (adaptation without reduction):

- **Object boundary** — a contract boundary is one CLI harness status-line component (`qoder`, `claude`, `codex`), matching the parent's one-contract-per-skill feature-boundary rule. There are no skill directories and no naming model for skills; the parent's naming-model section does not apply here.
- **Artifact ↔ contract mapping** — the parent maps skill directory name → contract file name 1:1; here the mapping (`<subdir>/<artifact>:<component>`) is declared in the pre-push hook (`OBJECTS`) because each harness component uses the artifact filename expected by its target CLI (`statusline-command.sh`, `statusline.sh`, `statusline.toml`).
- **No BACKLOG** — the parent's hook carries a backlog of pre-contract-system skills; here the contract system predates any component edit, so the backlog mechanism is absent by construction (RULE-contract-gate). The parent's `contracts/BACKLOG.md` (a store of agreed refactor proposals) is likewise absent: open questions live in the component contract's Risks/Q&A (precedent: QA-1) — see the adaptation research.
- **No release-skills boundary exception** — the parent's user-confirmed exception (repo mechanics as the skill's user-visible capability) has no object here: no component of this repo has repo mechanics as its capability.
- **RULE-contract-first retained** — the parent operationalizes contract-first through the episode cycle; this repo keeps the rule under its established name because the public text (`README.md`, «contract-first cycle») uses the term and the component contracts (RISK-2) reference the rule name.
- **RULE-obsolescence aligned with the parent** — the tombstone variant (contract kept as `status: superseded`) adopted on 2026-08-14 is superseded by the parent's canonical rule: removal removes contract, journal, IDX line, and README line in the same change; git history archives (see the adaptation research).
- **Backfill without a research file** — the initial Qoder baseline was backfilled by code inspection of the existing script; the multi-harness consolidation and its backfills (`claude`, `codex`) are documented in [../analysis/2026-11-15-multi-harness-statusline-research.md](../analysis/2026-11-15-multi-harness-statusline-research.md), and the harness-adaptation research begins at [../analysis/2026-08-14-harness-adaptation-research.md](../analysis/2026-08-14-harness-adaptation-research.md).
- **No application version, no sprints** — inherited from the parent: the chronicle is keyed by date (`CHANGE-YYYY-MM-DD-<tag>`), and no release versioning exists.
- **Reconstructability over brevity** — the Specification **MUST** carry the full component specification (behavior-level: segments, formats, colors, thresholds, fallbacks, caching algorithm, or declarative TOML keys), so contracts are as long as reconstruction requires. Terse-chronicle discipline still applies.
